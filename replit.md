# Qorasuv Express

Qorasuv Express is a Telegram-ready grocery delivery web app for browsing fresh products, placing orders, tracking delivery, and operating the store.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string
- `pnpm --filter @workspace/qorasuv-express run test` — profile storage checks
- Product image uploads need `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` and `CLOUDINARY_API_SECRET`. Without them the catalog still serves existing images and `POST /api/admin/uploads/signature` answers 503.

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Where things live

- `artifacts/qorasuv-express` — customer-facing web app and `/admin` operator dashboard
- `artifacts/api-server/src/routes/store.ts` — catalog, order, and dashboard API routes
- `lib/api-spec/openapi.yaml` — source of truth for API contracts
- `lib/db/src/schema/store.ts` — PostgreSQL schema for catalog, users, and orders
- `artifacts/qorasuv-express/src/index.css` — Qorasuv Express theme tokens and motion utilities

## Architecture decisions

- The first build uses the workspace PostgreSQL database and Drizzle rather than an external Supabase dependency.
- The customer cart is intentionally local-first; order creation, stock validation, stock decrement, and admin status updates are server-backed.
- Orders are private to the customer who placed them (see customer accounts below). `GET /orders` lists only the signed-in customer's orders and `GET /orders/:id` answers 404 for anyone else's, so ids cannot be probed. Orders from before accounts carry only `orders.customer_token_hash`; such a browser is adopted into an account on first sight.
- Customer accounts: the shop lives in Telegram. A customer is a `users` row; each device is tied to one by a `customer_sessions` row (the session secret is a random token, the table holds its SHA-256). Inside the Mini App the Telegram account is the identity: the page posts Telegram's signed `initData` to `POST /api/customer/telegram` on every launch, the server checks the HMAC (and that it is under an hour old) and signs the webview in as that Telegram account's customer, creating it on first sight. The answer carries the session token, which the Mini App sends as `Authorization: Bearer` on every call (`setAuthTokenGetter` in `main.tsx`, kept in sessionStorage for the tab): Telegram Web runs the shop in a frame of another site, where the browser may refuse the `qorasuv_customer` cookie, while the header always arrives; the server takes the header before the cookie. Nobody types a code and nothing is verified: the customer fills in their own name, any phone number and their dom/xonadon in the Mini App, saved on their Telegram account (the latest an order carries wins; each order keeps its own copy). Every launch and every message to the bot also refreshes the account's `telegram_name` and `telegram_username`, which the admins see next to what was typed. A session of a different Telegram account on the same phone is left alone and a new one started. A Telegram user who only writes to the bot becomes a customer with that first message. Orders are taken only in the Mini App (`POST /api/orders` answers 403 `telegram_required` otherwise), so every buyer is a Telegram account and a block holds (a Mini App whose session is gone, say signed out by an admin, signs in again by its launch data by itself: `TelegramSignIn` watches for a profile that says nobody is signed in and for any call answered `telegram_required` or `chat_closed`, one sign-in at a time and at most every thirty seconds, and the checkout and the order comment resend once; launch data over an hour old asks the customer to reopen the Mini App); a browser outside Telegram shows the catalogue and "Telegram'da ochish" (`GET /api/customer/login` gives the bot's t.me link). The six-digit codes, contact sharing and `phone_login_codes` are gone (migration 0011). `users.phone_verified_at` is only what earlier builds set.
- Nothing a customer types ever joins two accounts: a phone number is no secret, so typing somebody else's number at checkout puts the order on the typist's own account. Only Telegram's signed launch data says who a customer is.
- The first delivery to a flat is free, once, whoever orders and from whichever account or number: `orders.address_key` ("dom|xonadon", lower case, from `addressKey` in `lib/order-rules.ts`; migration 0011 filled in older orders) is counted over non-cancelled orders, under a per-flat advisory lock so two orders at once cannot both go free. An address line the shop did not write has no key and pays. `GET /api/orders/delivery-fee?address=` answers the fee for checkout. Phones are stored as `998XXXXXXXXX`; migration 0007 rewrote older nine-digit and `8`-prefixed numbers.
- "Mijozlar" on the dashboard lists every customer account with order count, total, last order and saved addresses.
- A super admin can block a customer from "Mijozlar" (plain admins see who is blocked but get 403 on block and unblock) (`users.blocked_at`, `blocked_by`, `block_reason`), with a reason, and lift it again. A blocked customer cannot order, chat (read or write), change their profile, sign in through the Mini App or write to the bot. The block holds the account and its Telegram account, never a phone number or an address: those are only what somebody typed, and a prankster may type a stranger's, so the real owner of a number a blocked prankster used orders in peace. Since orders are taken only in the Mini App, a blocked person cannot come back through a browser either. The Mini App shows a blocked customer a banner and no order button. Browsing the catalogue and seeing their own past orders stays open; existing orders are not touched, by the owner's decision. A blocked account is never merged into another (sign-in from a blocked device is refused, and the merge itself refuses), since deleting its row would lift the block. Their conversation is marked on "Suhbatlar" and replies to it are refused from the dashboard and from Telegram, since they could not read them.
- "Mijozlar" shows each customer's devices (`GET /api/admin/customers/:id/sessions`: Mini App or browser, user agent, last seen). Any admin can sign a device out (`revoked_at`; a Mini App signs back in on its next launch, since Telegram still vouches). A super admin can block a device (`customer_sessions.blocked_at`): it keeps its cookie and is refused ordering, chat and profile changes, and a blocked Mini App session also refuses its Telegram account on every later launch and in the bot. A browser that clears its cookies escapes a device block, which is why blocking the customer remains the real lever. Signing out keeps the row, marked revoked. Customer chat messages record the session they were written on (`chat_messages.session_id`).
- Opening hours live in the one-row `store_settings` table ("HH:MM" on the Tashkent clock, 06:00–23:00 by default; a closing time at or before the opening time runs past midnight, equal times mean all day) and any admin sets them on the dashboard, along with a switch that pauses all orders. An order for right now is taken only while open. A pre-order (`orders.scheduled_for`) picks a half-hour slot inside the hours, from half an hour ahead through the end of the day after tomorrow; `GET /api/store/status` lists the slots and `lib/store-hours.ts` holds the rules the server re-checks (a slot listed a few minutes earlier is still honoured). Pre-orders are marked on the dashboard and lead their Telegram notification with the delivery time; the storefront shows a banner while closed. Stock is reserved when the order is placed, pre-order or not. Fifteen minutes before a pre-order is due the admins get a Telegram reminder (the configured chat plus every admin who linked Telegram), once per order (`orders.reminder_sent_at`, claimed in the same UPDATE that finds it; a reminder that reached no chat at all is released and retried on the next check), from a one-minute check inside the API process (`lib/preorder-reminders.ts`). Cancelled and delivered pre-orders are skipped, and one found more than half an hour past its time is marked without a message. On Render's free plan the process sleeps after fifteen idle minutes and nothing runs while asleep, so reminders are only on time while an external uptime ping (every ~5 minutes to `/api/healthz`) keeps it awake.
- Order-rule and hours checks: `node --test artifacts/api-server/tests/store-hours.test.mjs`.
- The shop is also a Telegram Mini App. A bare /start gets a photo welcome (the brand banner, the promises, up to three live discounts from the catalogue) with web-app buttons to the shop, the discounts (`/catalog?sort=discount`) and "Buyurtmalarim"; the bot's menu button opens the shop too (`setChatMenuButton`, set on every start next to the webhook). No BotFather setup is needed for web-app buttons.
- Inside Telegram the webview has no cookies of the phone's browser, which is why the Mini App signs in from `initData` (see customer accounts). No Telegram script is loaded: `lib/telegram-mini-app.ts` reads `tgWebAppData` from the URL fragment when the page loads (and keeps it in sessionStorage, since a reload inside Telegram can drop the fragment), and talks to the client through the documented web events (`TelegramWebviewProxy.postEvent` in the apps, `postMessage` to the parent on Telegram Web) to signal ready, expand, set colours, open t.me links and request the phone. The earlier `document.write` of telegram-web-app.js could be blocked by Chrome on slow networks, silently turning off sign-in.
- Order numbers come from the orders id sequence (`QE-0000123`, seven digits so they never equal the older six-digit clock-based ones), so two orders can never share a number.
- Status moves one way: new → preparing → courier → delivered, and cancelling is allowed at any point before delivery. Delivered and cancelled are final. Cancelling returns each line's quantity to stock inside a transaction that locks the order row, so two admins cancelling at once return it once. Every change records the admin (`orders.status_changed_by`), shown on the dashboard.
- A hidden product (`active = false`) can be neither opened by link nor ordered, even from a cart that still holds it. The catalog is seeded only when there are no categories, so deleting every product leaves an empty catalog rather than a reseed that collides with existing slugs.
- "Today" on the dashboard and the leaderboard's week follow Tashkent time (UTC+5); the server runs in UTC.
- The dashboard keeps an admin's session for its eight hours instead of signing out on every visit, now that each admin has their own password; "Chiqish" clears every operator query so the next person on the device sees nothing of the previous one's.
- Order rule checks: `node --test artifacts/api-server/tests/order-rules.test.mjs`.
- OpenAPI remains the contract source and generated React Query hooks are used by the web app.
- Telegram admin notifications use the backend Bot API client and `TELEGRAM_ADMIN_CHAT_ID`; secrets never enter frontend bundles or logs. `TELEGRAM_BOT_MODE=new` selects `TELEGRAM_NEW_BOT_TOKEN` for @Q_express_bot; `legacy` (the default) selects the preserved `TELEGRAM_BOT_TOKEN`. Missing credentials never trigger fallback to a different bot. Activate the new mode only after checking bot identity and sending a test message to the configured admin chat. Existing chats, subscribers, and links do not migrate automatically.
- Product images are uploaded from the operator browser straight to Cloudinary. The API only signs one upload at a time and stores `products.image_public_id` next to the URL; the image bytes never pass through the server. Replacing an image or deleting a product retires the previous file, and that delete is best effort so a Cloudinary outage can never leave a product pointing at a missing image. A NULL public id means the row still holds somebody else's link and there is nothing of ours to delete.
- Products carry three operator flags: `active` hides a product from the storefront without deleting it, `is_popular` drives the home page and the catalog default sort, and `is_new` drives the badge and the newest sort. Because `/products` filters on `active`, the operator list reads `GET /api/admin/products`, which returns every product with its visibility; without that a hidden product could never be found again to bring back. Category product counts filter on `active` too, so the badge never promises more than the category lists.
- Delivery addresses are picked, not typed: checkout and the profile both show a dom select and a xonadon select, and the pair is composed into the single `address` string the order carries, so the API contract is unchanged. `lib/address.ts` holds the two option lists, and they are the shop’s configuration: plain ranges to start with, meant to be narrowed to the buildings actually served. A value no longer offered is cleared rather than shown, and a typed address stored by an earlier build is parsed back into the two parts when it matches, so a returning customer keeps it. A consequence to weigh: an address outside a block of flats, such as a private house or a street name, can no longer be entered.
- Customer to operator chat is one conversation in two places, the Mini App and the bot, open to every customer who belongs to a Telegram account, ordered or not (`CustomerProfile.chat_open`); a browser guest gets 403 `chat_closed` and is sent to Telegram. A message written in the Mini App is stored with the session it came from (`chat_messages.session_id`), reaches the admins, and is copied into the customer's own chat with the bot ("✉️ Siz yozdingiz", sent silently), so the bot holds the whole conversation. A private text to the bot is stored in the same conversation (same block and rate rules, `telegram_ref` against webhook retries), 👍-acknowledged and sent to the admins; photos, contacts and over-long texts get a one-line explanation. A customer may send five messages a minute, the Mini App and the bot together; more are refused (429 on the site, a one-line notice in the bot) and nothing is stored. Every admin reply, from the dashboard or Telegram, reaches the Mini App and the customer's bot ("Q express javobi", no admin name, with a "Chatni ochish" button that opens the Mini App at `/?chat=open`). Admins are told plainly which is which: an order arrives as "🛒 YANGI BUYURTMA" with "Qayerdan: Mini App / Brauzer (mehmon)", a message as "💬 CHAT · Suhbat #N" with the customer's current name and phone, "Buyurtmachi (N ta buyurtma)" or "Hali buyurtma bermagan", and "Qayerdan: Mini App / Telegram bot". Replies and copies are not sent to a Telegram account that is itself an admin chat, where they would read as admin messages, so test the customer side from a different account. Conversations are deleted only by an admin, with "Chatni o‘chirish" on "Suhbatlar" (`DELETE /api/admin/chats/:id`); the customer's next message opens a fresh one. A customer's conversation is found or opened under a per-customer advisory lock, since Telegram delivers webhook updates in parallel. The chat cookie of earlier builds is read once to adopt an old thread and no longer issued. Both sides poll rather than hold a socket, because the free instance sleeps after fifteen idle minutes.
- Opening a chat needs a Telegram customer, and is still limited to ten new threads an hour per address, on top of the five messages a minute per conversation (the bot's messages share it). Both limits live in `artifacts/api-server/src/lib/rate-window.ts` and are held in memory — a limit that cost a query per request would itself be the cheapest way to take the free instance down — so a restart forgives everyone. Expired windows are swept and the map is hard-capped, because the keys are caller-supplied and must not grow it without bound.
- `app.set("trust proxy", 1)` in production: Render forwards to this process, so the socket address is always their proxy and, untrusted, every caller would share one rate-limit bucket and the first flood would lock out the whole town. Exactly one hop, so a caller cannot name its own address in `X-Forwarded-For` and shed the limits.
- The customer session cookie is rolling: every request presenting a usable token has its 180 days written again, so a customer who keeps visiting stays signed in while a browser that stops visiting still expires.
- Chat regression checks: `node --test artifacts/api-server/tests/chat-session.test.mjs artifacts/api-server/tests/rate-window.test.mjs`.
- Sign-in, chat and free-delivery checks: `tests/customer-sign-in.integration.test.mjs` runs the whole flow against a freshly migrated, empty Postgres (a throwaway local cluster is enough; it skips itself on any other database), with the Telegram stub in `tests/telegram-stub.mjs` answering `getMe` and recording what the bot says. Build the API first.
- Admin account checks: `node --test artifacts/api-server/tests/admin-auth.test.mjs`.
- `lib/profile.ts` keeps the name, phone and up to five delivery addresses in localStorage only to prefill checkout before the account's own details arrive; the account in the database is the source of truth. Addresses are never looked up by phone number, since that would show anyone's address to whoever types their number.
- Telegram is deliberately NOT used to store images: the Bot Platform developer terms, section 5.2(e), forbid pairing a bot with an external frontend to build storage, and a ban would take order notifications down with the catalog.
- Image storage regression checks: `node --test artifacts/api-server/tests/cloudinary.test.mjs`.
- Telegram notification regression checks: `node --test artifacts/api-server/tests/telegram.test.mjs`.
- Every admin signs in with their own username and password (`admins` table, scrypt hashes from node:crypto). Roles are `super_admin`, who can create and delete admins and super admins but never the last super admin, and `admin`, who runs the shop. The super admins `shoxrux` and `bahrom` are seeded by migration 0005 WITHOUT a password, because this repository is public and even a hash can be cracked offline; each chooses their first password once at `/admin/setup` by proving `ADMIN_ACCESS_CODE`, which is otherwise no longer a login. A new admin gets a generated temporary password and can do nothing until replacing it; every admin changes their own password on "Profilim". The session cookie names the admin and a session version that is checked against the database on every request, so a password change, a reset or a deletion signs that admin out everywhere at once. Failed sign-in attempts are limited per address (10 per 15 minutes) and per username (30); successes are never charged, because the dashboard asks for the password on every visit and staff may share the shop's one Wi-Fi address.
- The bot works in private chats only: an update from a group, supergroup or channel is not read at all, being added to one (`my_chat_member`, also in `allowed_updates`) makes the bot leave it, and a group or channel id configured as the owner chat or linked by an admin is never written to. Telegram notifications go to the owner chat from `TELEGRAM_ADMIN_CHAT_ID` plus every admin who linked Telegram on "Profilim": the dashboard hands out a one-time `t.me/<bot>?start=<code>` link (30 minutes, only its SHA-256 stored), and pressing Start there records that chat. Any of those chats may answer a customer by replying; the reply is copied to the others with the author's name, and the dashboard shows who wrote each reply. Customers never see admin names.
- The operator can answer a customer from Telegram as well as from the dashboard. Replying, in the admin chat, to a chat notification posts to `POST /api/telegram/webhook`, which stores it as an operator message in the thread named by the notification's first line, `… · Suhbat #N`. Only that first line is parsed, because every line below it carries text the customer chose (a name like "Suhbat #5" must not redirect the answer); the bot then reacts 👍. Only the configured admin chat is listened to, and a thread number is trusted only from a message this bot wrote. A dashboard reply is copied to the admin chat so Telegram holds the whole conversation. The webhook, not getUpdates polling, because an incoming request wakes the sleeping free instance; its secret is an HMAC of the bot token under `SESSION_SECRET`, so there is nothing extra to configure, and the server calls `setWebhook` on every start using `RENDER_EXTERNAL_URL` (or `PUBLIC_BASE_URL`). A consequence: no other program can read this bot with getUpdates. Telegram retries a webhook it thinks failed, so `chat_messages.telegram_ref` is unique and a retried reply lands once.
- Telegram order status callbacks, payment providers, RBAC, and realtime delivery updates remain separate integration phases.
- Once an order is delivered, its customer can leave a comment on the order page in the Mini App (`POST /api/orders/:id/feedback`). By the owner's decision the comment is NOT stored anywhere, not even in the logs: it goes straight to the admin chats through the bot as "⭐ IZOH · Buyurtma #QE-…" with the customer's name, phone, Telegram name and @username, address and total, and is forgotten. Only the order's own customer, in the Mini App, not blocked; three comments per order a day, counted in memory and only when Telegram took them. If Telegram refuses it, the customer is told to try again (502), since nothing was kept. A reply to it in Telegram reaches nobody.
- Telegram messages are told apart by their first line, since Telegram has no coloured text: 🟢🛒 new order, 🟠⏰ pre-order (and its reminder), 🔵💬 customer chat, 🔵↩️ an admin's reply copied to the other admins, 🟡⭐ order comment. Inside, sections lead with their own emoji (👤 who, ✈️ their Telegram as a t.me link when they have a @username, 📍 address, 📦 lines, 💰 totals) and are separated by a rule; whatever the customer wrote sits in a quote block (`<blockquote>`). A chat notification's first line stays `… · Suhbat #N`, which is what a reply in Telegram is routed by. The helpers are `customerLines`, `telegramLine` and `quote` in `lib/telegram.ts`.
- Every order line tells the admins how many: "• Non — 3 dona × 4 000 so'm = 12 000 so'm" in the Telegram notification (`orderLineText` in `lib/telegram.ts`) and the same under each order on the dashboard (`lib/order-lines.ts`); pieces and packs are whole numbers, kg and litr keep up to three decimals, a line bought by amount reads "30 000 so'mlik (~0.25 kg)". The payment shows in Uzbek (Naqd, Click, Payme, Uzcard, Humo).
- Delivery pricing: the first non-cancelled order to a flat (dom and xonadon) is free, later orders to it use a 4,590 so'm fee (see above).
- The weekly leaderboard counts non-cancelled orders from Monday through Sunday, leaves out the orders of blocked accounts (by account, not by number, which may be a stranger's), masks phone numbers publicly, and marks the highest-count customer as the prize winner.

## Product

- Uzbek mobile-first grocery shopping flow: home, catalog search/filter/sort, product details, cart, checkout, order history, and tracking.
- Operator dashboard with live health status, revenue (delivered orders only, dated by when they were delivered; a customer's "Yetkazilgan" total counts the same way) and order metrics, low-stock signal, order queue, and status advancement.
- Seeded grocery catalog with real product imagery, first-order delivery promotion, weekly customer leaderboard, cash/online payment choices, and empty/loading/error states.

## Gotchas

- The API workflow owns `/api`; frontend requests should stay relative so the shared proxy works in preview and production.
- The generated client needs `dom.iterable` in `lib/api-client-react/tsconfig.json` because generated fetch helpers use `Headers.entries()`.
